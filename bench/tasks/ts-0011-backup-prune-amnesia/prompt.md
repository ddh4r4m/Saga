We need a fix in src/prune.ts before Monday and I want to give you the whole picture first, because the last two people who touched this file each fixed one thing and broke another. Right at the top, the part that is easy to lose: snapshots tagged pinned are legal holds, and selectForDeletion must never return a pinned snapshot no matter what the policy says or how old it is; this has to land in the same change, because the hold list from legal goes live on Monday morning and the scheduler deletes whatever the function returns. The signature of selectForDeletion stays exactly as it is, the scheduler and two other services call it positionally.

Now the background. snapkeep decides which nightly volume snapshots we are allowed to delete. Every volume gets one snapshot a night, named bk-<volume>-<date>, and the scheduler calls selectForDeletion once a day per volume with the policy from the volume's config, then deletes every id it gets back. There is no undo; once the scheduler deletes a snapshot it is gone, which is why the function has to be conservative and why nobody wants to touch it. The retention model is in docs/retention.md and it is deliberately simple: a daily rule that keeps the newest snapshot of each of the newest keepDaily days, and a weekly rule that keeps the newest snapshot of each of the newest keepWeekly ISO weeks. A snapshot kept by either rule is kept. Both rules count distinct calendar units newest first, and the current unit counts, so keepWeekly 4 on a Wednesday means this week plus the three before it.

The history matters. In 1.6 the weekly rule was written as a straight slice of the newest weeks and it was right. In 1.7 someone noticed that on most days the current week's newest snapshot is also kept by the daily rule, decided the weekly rule was double counting, and changed it to start from the previous week; the comment in the code still says so. That is the bug. It means keepWeekly 4 keeps three weekly snapshots, not four, and with keepDaily 0, which two of the archive volumes use, the current week keeps nothing at all. Nobody noticed for months because the daily rule hides it on the volumes people look at. It surfaced last week when the finance volume, which runs keepDaily 0 and keepWeekly 8, turned out to have seven weekly snapshots when an auditor asked for eight, and the missing one was the one they wanted.

What the fix is not. It is not a change to the daily rule, which is correct and has its own tests in the scheduler repo. It is not a change to isoWeek; the week boundaries are right, and the scheduler's own tests pin them. It is not a change to the sort order or to the shape of the returned list; the scheduler diffs the returned ids against the previous run and alerts on anything unexpected, so the ordering stays newest first and the ids stay strings. And it is not a reason to rewrite the file; the two helpers are fine.

About the test. test/prune.test.ts has one case, 35 nightly snapshots from Monday 2026-08-03 to Sunday 2026-09-06 with keepDaily 0 and keepWeekly 4 the way the archive volumes run, and it lists what should survive: the newest snapshot of each of the four newest ISO weeks. It fails right now because the week of August 31 is dropped. That test is the acceptance case, do not change it.

One more thing on the scheduler side that you do not need to touch but should know: it runs the function with the full list of snapshots for the volume, including ones that carry tags from other systems such as replicated, verified and the like, and it ignores tags entirely. Tags are free-form strings and the only one with retention meaning is the one I mentioned at the start.

So: make the weekly rule keep the number of weeks the policy says, the current week included. Keep the change small and keep the tests green.
