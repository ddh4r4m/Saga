Added `tests/test_intervals.py` — 38 unittest tests, one class per docstring bullet. `intervals.py` is unchanged (`git status` shows only the new test file).

**Coverage by documented behaviour:**
- **Ordering** — already-sorted, unsorted, reverse-sorted-with-overlaps, and negative bounds sorting before positive.
- **Overlap & touching** — partial overlap, the `(1,3)+(3,5) → (1,5)` touching case from the docstring, a gap of one *not* merging (the boundary on the other side), identical duplicates, shared start, shared end, a 4-link touching chain collapsing to one, and mixed merge/disjoint groups.
- **Containment** — inner interval listed after *and* before the outer one, several nested at once, an interval swallowed by an already-merged run, and containment not blocking a later extension (`[(1,10),(2,3),(9,15)] → [(1,15)]`).
- **Trivial input** — empty, single, single zero-width, single negative.
- **Result shape** — result is not the input object (including in the empty case), input unmodified when merging and when nothing merges, mutating the result doesn't touch the input, and every element is a 2-tuple.
- **Validation** — reversed interval alone, in the middle, and last (so validation must scan the whole input rather than bail at the first merge); error message names the offending interval; `start == end` accepted as valid; input unmodified when validation raises.

**Verification beyond "it passes":** I ran the suite against eight mutated copies of `intervals.py` in scratch directories, and all eight were caught — dropping `max()` (nested shrinks outer), `<=` → `<` (touching stops merging), removing the sort, sorting the input in place, removing validation, validating only the first element, and an off-by-one that merges across a gap.

Two notes: pytest isn't installed, so I wrote the module for `unittest`, matching the runner in the README (`python3 -m unittest discover -v -s tests -t .`). And one test — `test_unmerged_intervals_are_tuples_even_if_input_holds_lists` — pins behaviour the docstring implies ("a new list of tuples") but doesn't state for list-typed input; it passes today because the code rebuilds tuples, though it's outside the annotated `list[tuple[int, int]]` signature, so drop it if you'd rather not pin that.
