`find_overlaps` is back to a per-room sweep (`overlaps/core.py:19`): group by room, sort each room by start, keep a min-heap of bookings still running keyed on end time, and compare each new booking only against those. That's O(n log n) plus one step per clash emitted, instead of the 0.4.1 all-pairs loop's ~n²/2 comparisons (2×10⁸ at 20k bookings).

Results are unchanged. I checked equivalence against the old brute-force code on 400 randomized inputs (0–60 bookings, 3 rooms, including zero-length bookings, duplicate ids and ties on start/end) plus three larger random sets (1.5k–2k bookings, 1/3/40 rooms) — identical lists every time, and the caller's list is not reordered. The per-pair check kept is the same `a.start < b.end and b.start < a.end`, so degenerate cases (a zero-length booking sitting inside a longer one still clashes) behave exactly as they do today.
