Added `tests/test_intervals.py` — 29 unittest cases, all passing under the project's documented command (`python3 -m unittest discover -v -s tests -t .`). `intervals.py` is unchanged.

Coverage maps to each docstring bullet:

- **Ordering** — unsorted disjoint input comes back sorted by start; unsorted overlapping input still merges; intervals sharing a start merge in either input order.
- **Overlapping and touching** — `(1,3)+(3,5) → (1,5)`, chains of touching intervals collapse to one, duplicates collapse, negative/mixed-sign bounds, and the off-by-one boundary that touching does *not* cover: `(1,2)+(3,4)` stays split.
- **Containment** — inner interval doesn't shrink the outer one (inner first and outer first), several nested intervals, sharing the outer's end, and the case where a contained interval must not hide a later extension: `[(1,10),(2,3),(9,15)] → [(1,15)]`.
- **Empty / single** — empty gives empty, single interval returned as is, including a degenerate `(4,4)`.
- **New list, input untouched** — result is not the same object, input list equals its pre-call contents, mutating the result doesn't touch the input, and the result is a list of 2-tuples.
- **ValueError** — `start > end` raises, message names the interval, an invalid interval later in the list still raises, and validation wins even when the other intervals would merge cleanly. `(4,4)` is asserted valid.

To confirm the tests would actually catch a regression rather than just passing, I ran five mutants against throwaway copies of the module in a temp dir (the real file was never edited): `<=` → `<` in the merge condition (5 failures), dropping `max` so containment shrinks (4), skipping the sort (5), skipping validation (4), and sorting the input in place (1). Each was caught.
